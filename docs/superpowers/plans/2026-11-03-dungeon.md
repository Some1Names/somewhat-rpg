# Dungeons Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Private party dungeon runs: a portal, difficulty tiers, a seeded chain of hand-built rooms ending in a boss, shared revives, and a once-per-player completion chest.

**Architecture:** `DungeonConfig` (pure, Lune-tested) holds dungeons, tiers and every rule; `DungeonRun` (server module) builds and runs one instance in a far-away slot of `workspace.DungeonRuns`; `DungeonServer` is the portal and the `DungeonAction` remote; `DungeonMenu`/`DungeonHUD` are the client. Same shape as `RaidConfig`/`RaidServer` and `FastTravelConfig`/`FastTravelServer`.

**Tech Stack:** Luau (Roblox), Lune for tests (`tests/run.sh`), Studio for the smoke test.

**Spec:** `docs/superpowers/specs/2026-11-03-dungeon-design.md`

## Global Constraints

- UI is square: no `UICorner` in `DungeonMenu`/`DungeonHUD`.
- Parties: `Party.Of(player)` and `Party.Mates(player)` (`ServerScriptService/Party`), `PartyRules.MaxMembers = 4`; solo is allowed.
- Rewards: `PlayerStats.AddYen(player, amount, source)` and `PlayerStats.AddXP(player, amount, source)`; materials are `Mat_<key>` attributes capped with `DropConfig.Fit`.
- Enemies: a model tagged `Enemy` with an `EnemyType` attribute is picked up by `EnemyAI` automatically; kills are seen through `Damage.OnKill(listener)`. All player damage goes through `Damage.Deal`.
- Gear is optional: if `ServerScriptService.Gear` exists use `Gear.Grant`; otherwise the chest pays materials instead. Never error when it is missing.
- Pure modules take no Roblox types (Lune must `require` them). Match surrounding code: comment density, tabs, naming. No final VFX (the owner's).
- Studio is the source of truth: new scripts are applied to Studio by a local session afterwards; list the Studio instances needed.

## Review Focus

- A run must always free its slot and destroy its folder, including after a script error, a time-limit fail, and every player leaving.
- Two parties starting at once must never share a slot, a room instance, or a cooldown.
- A player who disconnects and rejoins must not re-enter a run or keep a cooldown-free state; the cooldown is per player, set at run start.
- A dead player at the last revive, a leader who leaves mid-run, and a solo run must each end or continue cleanly.
- A tampered `DungeonAction` call (unknown dungeon id, tier out of range, non-leader start, player out of portal range) must be refused with a reason, never start a run.

- Test: `tests/DungeonConfig.spec.luau`

- Produces (on `DungeonConfig`):

### Task 2: DungeonRun (one instance)

**Files:**
- Create: `src/ServerScriptService/DungeonRun.luau`

**Interfaces:**
- Consumes: Task 1's `DungeonConfig`; `Damage.OnKill`; `CollectionService`; room models in `ServerStorage.DungeonRooms/<dungeon id>` (room contract in the spec); enemy models for each `EnemyType` in `ServerStorage.DungeonEnemies` (a Studio task; if a type's model is missing, warn once and skip so the run still completes).
- Produces: `DungeonRun.Start(dungeonId: string, tierIndex: number, players: { Player }, seed: number): (Run?, string?)` (nil + why: "Dungeons are busy", "Unknown dungeon", "Room models missing"); `DungeonRun.OfPlayer(player): Run?`; `DungeonRun.Leave(player)`; `DungeonRun.OnEnded(callback: (run, result: "win"|"fail"|"abandon"|"timeout") -> ())`; `Run = { id, dungeon, tier, players, revivesLeft, roomIndex, cleared: boolean, folder }`. State changes are mirrored to each player's attributes `DungeonRoom` ("2/5"), `DungeonRevives`, `DungeonEndsAt` for the HUD.

- [ ] **Step 1: Implement slot handling**: a table of `MaxRuns` slots; `acquire()` returns the first free index or nil; `release(index)` always called in `end` via `pcall`-guarded cleanup so an error cannot leak a slot (Review Focus 1).
- [ ] **Step 2: Implement building**: clone rooms in `BuildLayout` order into `workspace.DungeonRuns/<runId>`, positioned from `DungeonConfig.SlotPosition(slot)`; snap each room by `PrimaryPivot` so its `In` part meets the previous `Out` part; teleport the players to the start room's `In`.
- [ ] **Step 3: Implement room play**: when a player enters the next room's trigger (its `In` part touched), spawn that room's `DungeonSpawn` enemies (clone the `EnemyType` model, set attribute `MaxHealth`/level from the tier's `enemyLevel`, tag `Enemy`, parent in the run folder); count them and unlock the room's `Door` when all die (via `Damage.OnKill` plus the model's `Humanoid.Died`); mark a checkpoint. Treasure and start rooms spawn nothing. The boss room spawns the `bossType` enemy and a `Chest` part (inactive) that activates when the boss dies (set `cleared`).
- [ ] **Step 4: Implement deaths and ending**: on a player death, if `revivesLeft > 0` decrement and respawn them at the last checkpoint after 5 s; else mark them down; `DungeonConfig.RunFailed(revivesLeft, aliveCount)` ends the run as `"fail"`. End also on `RunTimeLimit` (`"timeout"`), everyone left (`"abandon"`), or the chest opened by all/boss cleared and 60 s passed (`"win"`). Ending teleports players back to the portal's spawn, destroys the folder, releases the slot, fires `OnEnded`. A player leaving or disconnecting for `DisconnectGrace` counts as left; if the run's players are all gone the run ends `"abandon"`.
- [ ] **Step 5: Compile check** (Lune `luau.compile` on the file; Lune path `C:\Users\Admin\tools\lune\lune.exe`). Expected: no errors.
- [ ] **Step 6: Commit** `git add src/ServerScriptService/DungeonRun.luau` and `git commit -m "Dungeons: DungeonRun builds and runs an instance"`.

### Task 3: DungeonServer (portal, remote, cooldown, chest)

**Files:**
- Create: `src/ServerScriptService/DungeonServer.server.luau`
- Modify: `src/ServerScriptService/PlayerStats.luau` (saved text for the cooldown, see Step 1)

**Interfaces:**
- Consumes: Tasks 1–2; `Party.Of`/`Party.Mates`; `PlayerStats.AddYen`/`AddXP`; `DropConfig.Fit`/`Attribute`; `Gear.Grant` if present.
- Produces: the `DungeonAction` RemoteFunction (made by script): `InvokeServer("start", dungeonId, tierIndex) -> ok, why`, `("leave") -> ok`, `("info", dungeonId) -> { tiers, cooldownLeft }`; chest opening hooked to a `ProximityPrompt` on each run's `Chest` part (created by `DungeonRun` or here).

- [ ] **Step 1: Cooldown storage**: add `DungeonLastRun = ""` to `PlayerStats` `TEXT_DEFAULTS` (a plain number string, `os.time()` at run start) and read/write it through the player attribute; account for it in `TEXT_LENGTHS` only if the default 200 is too short (it isn't).
- [ ] **Step 2: Portal**: for each model tagged `DungeonConfig.Tag` add a `ProximityPrompt` that opens the menu client-side (the client does this, see Task 4); the server only checks range in `start`.
- [ ] **Step 3: `start` handler**: validate argument types; dungeon and tier exist; caller is the party leader (or solo); every party member is within `Range` (reuse `FastTravelServer`'s range-to-tag pattern) of the portal; `DungeonConfig.CanStart` for each member; call `DungeonRun.Start`; on success write `DungeonLastRun` for every member at once. Refuse with a reason otherwise (Review Focus 5). Per-player busy flag against double calls.
- [ ] **Step 4: Chest**: on a run's chest prompt, once per player per run: roll `DungeonConfig.ChestRolls`, pay `AddYen`/`AddXP`, add materials (clamped with `DropConfig.Fit`), and grant gear with `Gear.Grant` when the module exists; otherwise add the tier's `chestMaterials` instead. A second open by the same player returns nothing.
- [ ] **Step 5: Compile check** the file and `PlayerStats`; run `bash tests/run.sh`. Expected: no errors, all specs pass.
- [ ] **Step 6: Commit** `git add src/ServerScriptService/DungeonServer.server.luau src/ServerScriptService/PlayerStats.luau` and `git commit -m "Dungeons: portal, start/leave remote, cooldown and chest"`.
